# Startup Company Design

## Overview
Use this skill to think about a startup as a system of functions that all must exist somehow, even if one founder is carrying many of them. The goal is to expose hidden company needs early enough to avoid structural weakness.

## When to Use
Use this skill when the main problem is **what the company actually needs as a whole**.

Typical triggers:
- founder is over-simplifying the company into product vs tech only
- important company functions are being ignored
- one founder or tiny team needs a better map of the whole operating model
- structural blind spots are causing repeated execution pain
- the company needs clearer functional coverage before hiring or scaling

Do **not** use this as the main skill when:
- the task is weekly operating rhythm → use `founder-operating-system`
- the task is org structure after hiring → use `org-design-after-first-hires`
- the task is narrow functional advice that already belongs to another specific skill

## Core Principle
A startup is not a product plus code alone. It is a set of functions that must all be handled somehow, even if the same person covers many of them at first.

## Always cover
- company functions that must exist
- current founder/team coverage
- hidden weak spots
- stage-appropriate function depth
- which gaps matter now versus later
- likely next structural bottleneck

## Workflow
1. Identify stage, product model, and current team reality.
2. Map the core company functions that exist whether or not they are formally named.
3. Diagnose where the company is structurally overbuilt, underbuilt, or dangerously missing coverage.
4. Recommend what needs real attention now versus later.
5. Connect function gaps to likely execution and risk consequences.

## Output format
Return:
1. company-design diagnosis
2. current function map
3. missing or weak functions
4. now-vs-later focus
5. next structural risks

## Common pitfalls
1. **Reducing the company to product and engineering only.** Many failures start outside the product itself.
2. **Trying to formalize every function too early.** Awareness does not require bureaucracy.
3. **Ignoring invisible operator work.** Legal, finance, support, and GTM still exist.
4. **Confusing org chart with function coverage.** Titles do not guarantee the work is actually handled.
5. **Adding people before clarifying function need.** Hiring into confusion compounds confusion.

## Verification checklist
- [ ] I mapped the company as functions, not just roles or titles.
- [ ] I distinguished current-stage needs from future-stage structure.
- [ ] I identified missing or under-covered functions.
- [ ] I tied structure gaps to practical operating risk.

## Examples
### Example: solo founder setup
Return:
1. The founder is acting across product, GTM, finance, and support, but only product work is visible.
2. Name the core functions explicitly even if one person owns many of them.
3. Identify which functions need light process now and which can stay informal.
4. Expose the likely next failure point before hiring reactively.
5. Keep the map simple enough to guide action.

### Example: pre-scale team confusion
Return:
1. The issue is uneven function coverage, not just lack of more people.
2. Support, finance, and GTM coordination are weaker than product output.
3. Clarify function ownership before expanding headcount.
4. Use the company-design view to guide next hires and rituals.
5. Revisit the map as stage and business model change.
