# Customer Support and Feedback Ops

## Overview
Use this skill to design support operations that resolve issues, protect trust, and turn repeated friction into product learning. The goal is not just answering tickets faster. The goal is a support system that improves the business.

## When to Use
Use this skill when the main problem is **reactive customer issue handling and support-system design**.

Typical triggers:
- support queue is messy
- issue triage is inconsistent
- bug/status communication is weak
- customer complaints are not turning into product insight
- support work is hurting retention or brand trust
- support ownership is unclear

Do **not** use this as the main skill when:
- the task is post-sale success lifecycle design → use `customer-success-for-b2b`
- the task is broader roadmap prioritization rather than support operations → use `product-discovery-and-prioritization`
- the product has almost no support volume and the question is hypothetical only

## Core Principle
Good support is not just response handling. It is a trust-preserving operating system that turns customer pain into resolved issues, clearer communication, and better product decisions.

## Always cover
- intake and triage flow
- severity and prioritization logic
- response and communication norms
- bug / issue ownership
- feedback loop into product
- retention or trust implications

## Workflow
1. Clarify support volume, product type, and current failure mode.
2. Diagnose whether the main issue is triage, ownership, communication, tooling, or feedback capture.
3. Recommend a support workflow proportionate to stage.
4. Define severity, escalation, and communication rules.
5. Turn repeated issues into product and process improvement.

## Output format
Return:
1. support-ops diagnosis
2. recommended workflow and ownership model
3. triage / severity / communication guidance
4. feedback and product-learning loop
5. next system improvements

## Common pitfalls
1. **Treating support as inbox cleanup only.** That loses product intelligence.
2. **No severity discipline.** Teams then treat every issue as equally urgent or equally ignorable.
3. **Vague bug communication.** Silence erodes trust fast.
4. **No owner for recurring pain.** The same problems keep cycling.
5. **Using support work only reactively.** Good support teaches the product team.

## Verification checklist
- [ ] I identified the actual support-system failure mode.
- [ ] I included triage, severity, and ownership logic.
- [ ] I connected support to trust and retention, not just speed.
- [ ] I built a loop from support pain into product improvement.

## Examples
### Example: messy early support
Return:
1. The issue is weak triage and ownership, not merely slow replies.
2. Add simple severity rules and one owner per issue path.
3. Use clear customer-facing status language for bugs and delays.
4. Group repeated complaints by underlying problem, not ticket wording.
5. Review support themes weekly with product.

### Example: retention-sensitive complaints
Return:
1. Certain support failures are trust failures, not just workflow misses.
2. Escalate customer-impacting issues faster.
3. Add explicit follow-up on high-friction accounts.
4. Feed churn-risk patterns into success and product teams.
5. Track repeat pain themes, not just ticket counts.
